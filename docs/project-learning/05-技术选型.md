# 05 技术选型

## 1. 总体技术栈

| 层级 | 技术 |
|---|---|
| 前端 | React 18 + TypeScript + Vite |
| 后端 | NestJS 10 + TypeScript |
| 数据库 | PostgreSQL 16 |
| ORM | Prisma 5 |
| Monorepo | npm workspaces |
| 共享逻辑 | packages/shared |
| 测试 | Node 内置 node:test |
| 部署 | Docker Compose + nginx + 腾讯云脚本 |

## 2. 为什么选择 TypeScript

本项目业务规则复杂，数据结构多，前后端都需要处理：

- 用户角色。
- 题目类型。
- 知识点。
- 学习计划。
- 错题记录。
- 掌握度。
- 测评报告。

TypeScript 的价值：

- 让前后端接口类型更清晰。
- 降低重构风险。
- 对教育业务中的复杂 DTO 更友好。
- 配合 `packages/shared` 共享领域类型和纯函数。

面试表达：

> 我选择 TypeScript 不是为了追求语法，而是因为教育提分系统的数据模型复杂，类型可以提前约束错题、计划、测评、知识点这些核心对象，降低前后端口径不一致的风险。

## 3. 为什么前端选择 React + Vite

React 适合构建复杂交互型学习工作台：

- 学生首页。
- 今日计划。
- 做题面板。
- 错题详情。
- 知识图谱。
- 报告工作台。
- 管理端审核页面。

Vite 的价值：

- 本地启动快。
- 构建现代前端资源。
- 对 TypeScript 和 ESM 支持自然。
- 适合中小型产品快速迭代。

当前没有使用 React Router，而是用 section 状态切换。这适合当前“单页学习工作台”的产品形态，但未来如果要做 SEO、公开页面或复杂深层路由，可以再引入路由库。

## 4. 为什么后端选择 NestJS

NestJS 的价值：

- 模块化清晰：Auth、Questions、Study、ScoreCenter 可以拆成模块。
- 装饰器写法适合表达 Controller、Guard、DTO。
- 适合中大型业务系统。
- 方便接入全局限流、ValidationPipe、Guard。

本项目后端模块划分：

- `AuthModule`：认证与账号。
- `QuestionsModule`：题库与导入。
- `StudyModule`：学习闭环。
- `ScoreCenterModule`：今日提分和知识节点能力。
- `OperationsModule`：操作日志。
- `PrismaModule`：数据库基础设施。

面试表达：

> 我用 NestJS 是因为这个项目不是简单 CRUD，而是包含认证、题库、学习计划、错题复盘、报告、管理端多个业务域。Nest 的模块边界和 Guard 机制能让权限和业务层次更清楚。

## 5. 为什么选择 PostgreSQL + Prisma

PostgreSQL 适合本项目的原因：

- 关系数据多：用户、题目、知识点、练习记录、计划、复习、导入任务之间关系复杂。
- 支持数组和 JSON 字段：适合题目选项、公式、导入结果、推荐原因等半结构化数据。
- 事务能力可靠：适合计划生成、导入确认、题目版本化等场景。

Prisma 的价值：

- Schema 可读性高。
- 类型生成友好。
- 迁移管理清晰。
- 查询代码比手写 SQL 更适合快速迭代。

面试表达：

> 这个系统既有强关系模型，也有一些半结构化字段，所以 PostgreSQL 比纯文档数据库更合适。Prisma 则帮助我把数据库 schema、迁移和 TypeScript 类型连接起来。

## 6. 为什么使用 packages/shared

`packages/shared` 是技术选型里的关键设计。

它解决的问题：

- 判题、错因、掌握度、计划等规则不能前后端各写一套。
- 前端需要展示推荐结果，后端需要计算推荐结果，类型必须一致。
- 测试可以直接验证领域纯函数。

适合放在 shared 的代码：

- 类型定义。
- 纯函数。
- 无数据库依赖的算法。
- 无浏览器依赖的业务规则。

不适合放在 shared 的代码：

- React 组件。
- Nest service。
- Prisma 查询。
- 浏览器 API。

## 7. 为什么使用 node:test

当前测试使用 Node 内置 `node:test`，不是 Jest/Vitest。

优点：

- 零额外测试框架复杂度。
- 启动快。
- 对文件级静态断言和纯函数测试足够。
- 适合当前大量“架构约束 + 业务规则”的测试。

缺点：

- 前端组件交互测试能力不如 Testing Library + Vitest。
- E2E 仍需要 Playwright 或浏览器自动化补足。

面试表达：

> 当前项目更重业务规则和架构约束，所以 node:test 足够覆盖大量核心逻辑。后续如果要提升前端交互质量，我会补充 Vitest/Testing Library 和 Playwright。

## 8. 为什么使用 Docker Compose 部署

本项目生产部署需要同时管理：

- Web/API 应用。
- PostgreSQL。
- nginx。
- 数据卷。
- 备份任务。

Docker Compose 的价值：

- 一台腾讯云服务器即可部署完整系统。
- 环境一致，减少“本地能跑线上不能跑”。
- 数据库卷和导入资产卷可以独立持久化。
- 方便做健康检查、回滚和备份。

生产命令集中在：

- `compose.production.yml`
- `deploy/tencent-ip/deploy.sh`
- `npm run prod:*`

## 9. 当前选型不足

### 9.1 前端没有路由库

当前 section 状态足够支撑学习工作台，但未来如果需要：

- 公开 SEO 页面。
- 深层页面 URL。
- 多角色复杂路由。
- 面包屑和权限路由。

可以考虑引入 React Router 或 Next.js App Router。

### 9.2 App.tsx 和 StudyService 偏大

这是当前维护性风险。后续可以拆成：

- practice service。
- wrong-question service。
- report service。
- plan service。
- assessment service。
- student app shell。
- student workflow hooks。

### 9.3 前端测试体系还可以增强

当前测试偏静态约束和业务纯函数，后续可以增加：

- 组件测试。
- 视觉回归。
- Playwright E2E。
- 线上 smoke test。

## 10. 技术选型总结

这套技术栈适合“中等复杂度、强业务规则、快速迭代”的教育产品：

- React + Vite 提供快速前端开发。
- NestJS 提供后端模块化。
- PostgreSQL + Prisma 支撑复杂关系数据。
- shared package 保证核心规则一致。
- Docker Compose 支撑低成本私有化部署。

如果未来要升级到更商业化的 AI 教育产品，可以在现有架构上扩展：

- RAG 服务。
- 向量数据库。
- 更完整的 E2E 测试。
- 更细的服务拆分。
- 更强的监控与数据分析。
